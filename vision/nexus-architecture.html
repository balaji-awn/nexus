Nexus Architecture

An orchestrator that reads a prompt, picks the right few agents out of thousands on the AI Platform Service, runs them, and merges their results into one cited answer.

Python · FastAPI · LangGraph Postgres + pgvector · Redis All agents read-only (v1) Platform API contract is assumed

Part 1

Executive summary

The problem. The AI Platform Service hosts thousands of specialized agents. A user asks one question in plain language, and answering it may need two or three of those agents, sometimes in a particular order. No caller can be expected to know which agents to use, and no LLM can be shown thousands of agents at once and pick well.

What Nexus does. Nexus takes the prompt and splits it into sub-tasks. For each sub-task it narrows thousands of agents down to the best five to ten. It then has a planning agent choose which ones to call and with what inputs, runs them in parallel where it can, checks whether the results answer the question, and finally merges everything into one answer that says which agent supplied each fact.

How it is split. Retrieval decides what is possible: a registry of every agent, searched with fast embeddings and keywords, then scored by an LLM agent. The orchestrator decides what to actually do: planning, running, reflecting and answering, built on LangGraph for durable state.

The main constraint. Nexus cannot call an LLM directly. Every LLM step is itself an agent on the platform, so we create six "system agents" by hand for Nexus's own reasoning. Every platform call is asynchronous: submit, get an execution ID, poll until it finishes.

Part 2

Concepts

The ideas the design rests on, and why each one is used here.

Why not give the LLM every agent?

The usual way to let an LLM use tools is to list them all in its prompt and let it choose. That breaks at this scale, for three reasons:

  • Size. Each agent's description and input schema runs to a few hundred tokens. Thousands of agents would not fit in any prompt.
  • Accuracy. Models choose tools less accurately as the list grows, especially when many tools look alike: "IP reputation", "domain reputation", "IP geolocation".
  • Latency. A larger prompt makes every planning call slower, and here every call is also a polled round trip.

So Nexus treats tool selection as a search problem. It finds a short list first, and only that list goes to the planner.

Recall, then precision

Retrieval has two stages because the two jobs need different tools.

Stage 1 · Recall

A bi-encoder embeds the sub-task and each agent separately, so agent vectors are computed once in advance. Comparing vectors takes milliseconds even across thousands of agents. It is coarse, so it keeps about 50 candidates. The goal is to not miss the right one.

Stage 2 · Precision

A scorer reads the sub-task and each candidate together, so it can judge details like "this agent takes a domain, but we have an IP". This is far more accurate and far too slow for thousands of agents, which is why it only sees the 50. In Nexus the scorer is the nexus-scorer agent.

Hybrid search and rank fusion

Embeddings capture meaning: "is this address dangerous" lands near "IP reputation lookup" even with no words in common. They are weak on exact terms such as product names, CVE IDs or log source names. Keyword search (BM25) is the opposite. Running both and merging the rankings covers both cases.

The rankings are merged with Reciprocal Rank Fusion. It uses only each agent's position in each list, so the two kinds of score never have to be put on the same scale:

RRF(agent) = Σ over lists 1 / (k + rank in that list), k = 60

An agent ranked 1st by vectors and 4th by keywords scores 1/61 + 1/64 ≈ 0.032. An agent ranked 1st by only one list scores 1/61 ≈ 0.016. Agreement between the two lists wins.

Plans as graphs, in a bounded loop

A plan is a small directed acyclic graph: steps are agent calls, and edges mean "needs output from". Steps with no edge between them run in parallel. A step that needs a list of users waits for the step that finds them, and may fan out into one call per user.

Results can raise new questions. If the IP is malicious, the natural next question is what those users did afterwards. So the orchestrator runs a loop: retrieve → plan → execute → reflect. This is the familiar "reason, act, observe" agent pattern. It is bounded by a loop count, a call count and a time limit, so a confused model cannot loop forever.

Async jobs, backoff and not running twice

The platform accepts a job and returns an execution ID straight away, and the result has to be polled for. Polling too often wastes calls. Polling too rarely adds delay. Exponential backoff polls quickly at first, when fast agents finish, then spaces polls out:

wait(n) = min(0.5 s × 2ⁿ, 10 s) × random(0.8 … 1.2)

The random factor, called jitter, stops hundreds of polls that started together from all landing in the same instant.

A submit that times out is the dangerous case: the platform may have created the execution even though no reply came back. Resubmitting would run the agent twice. Nexus never resubmits blindly, and it saves each execution ID before doing anything else, so after a crash it picks up polling the same ID.

Durable state and graceful failure

A request can last minutes and pause for a clarifying question, so its state cannot live only in memory. LangGraph saves a checkpoint after every step to Postgres, and any Nexus pod can resume from it.

When one agent fails, the request does not fail. Nexus answers from what succeeded and lists what is missing. A partial answer with a clear gap is more useful to the caller than an error.

Measuring routing

  • Recall@50: how often the correct agent is among Stage 1's 50. If it isn't there, nothing later can recover it.
  • Hit@5: how often it is among Stage 2's top 5, the list the planner sees.
  • MRR (mean reciprocal rank): the average of 1 / its position. It rewards ranking the correct agent first.

A test prompt must never also be used to build the index. Otherwise retrieval is tested on text it has already seen, and the scores come out higher than they will be in real use.

Part 3

High-level design

Components

Nexus runs in Kubernetes next to the AI Platform Service. Its only outward dependency for reasoning and data is the platform: system agents for its own LLM steps, domain agents for the actual work, and the catalog for what exists.

ComponentResponsibility
Nexus APIAccepts prompts from the backend service, returns a request ID, serves status and results, takes answers to clarifying questions, sends callbacks.
OrchestratorThe LangGraph graph: intent, retrieval, planning, execution, reflection, synthesis. Owns budgets and checkpoints.
RetrievalStage 1 hybrid search over the registry, then Stage 2 scoring through nexus-scorer.
Embedding modelTurns agent descriptions, example prompts and sub-tasks into vectors. Runs in the Nexus process.
Platform clientThe only code that talks to the platform. Submits, polls, validates against schemas, retries safely, records latency.
Catalog syncMirrors the platform catalog into the registry, re-indexes changed agents, and checks system agents against their specs.
Postgres + pgvectorRegistry (agents, examples, vectors), LangGraph checkpoints, requests and steps, feedback.
RedisCaches catalog lookups and routing decisions, and tenant-keyed agent results.

Request pipeline

Every request follows the same path. Only two places branch: a clarifying question before work starts, and the reflection loop after each round.

Two kinds of agents

Every agent lives on the platform, but Nexus uses them in two different ways.

System agentStepGetsReturns
nexus-intentIntent analysisPrompt, any earlier clarificationSub-tasks, or one clarifying question
nexus-scorerRetrieval Stage 2All sub-tasks, about 50 candidate summaries eachScore 0–10 per candidate per sub-task
nexus-plannerPlanningSub-tasks, top candidates with input schemas, earlier resultsSteps with agent, inputs and dependencies
nexus-reflectorReflectionPrompt, plan, results so farDone, or a list of new information needs
nexus-synthesizerSynthesisPrompt, all results with their sourceAnswer with citations, and gaps
nexus-example-generatorOffline onlyOne domain agent's name, description, schemasAbout 10 realistic prompts for it

Domain agents are the thousands of specialized agents that do the actual work, such as IP reputation lookup or user connection search. Nexus finds them by retrieval and calls them from the plan. System agents are tagged in the registry and never appear in retrieval results.

Hand-created

The platform has no API for creating agents, so system agents are set up by hand. The repo holds each one's prompt and schemas as the reference copy. At startup Nexus compares them with the catalog and refuses to start if one is missing or its schema differs.

Part 4

Low-level design

Modules

nexus/
  api/             FastAPI routes, request/response models, callbacks
  orchestrator/    LangGraph graph, state, nodes, budgets
  retrieval/       stage 1 SQL, rank fusion, stage 2 scorer call
  registry/        tables, catalog sync, embedding model wrapper
  platform/        client, shared poller, adapter (paths, headers), errors
  system_agents/   one folder per agent: prompt.md, input.schema.json,
                   output.schema.json; startup check against catalog
  eval/            example generation, recall@50 / hit@5 / MRR reports
  fakeplatform/    fake AI Platform Service for development and CI
  observability/   OpenTelemetry tracing, structured logs

platform/adapter.py is the only file that knows the platform's URL paths, header names and field names. When the real API differs from the assumed one, that file changes and nothing else.

Data model

  • Several vectors per agent. Each agent has one vector for its description, plus one per indexed example prompt. Its vector score is the best match among them. A user's wording is often closer to an example prompt than to the description.
  • Leases. lease_owner and lease_until on REQUEST let a running pod claim a request. If the pod dies, the lease expires and another pod resumes from the checkpoint.
  • Steps keep execution IDs. Every agent call is a row with its platform execution ID. That gives an audit trail and makes resuming safe.

Orchestration graph

The LangGraph graph, node by node. State is one typed object that holds the prompt, tenant, sub-tasks, candidates, plan, step results, loop counter and budget counters. It is checkpointed after every node.

NodeDoesPlatform calls
intentSplits the prompt into sub-tasks, or asks a question1 system
recallStage 1 for each new sub-task (SQL + embedding, no LLM)0
scoreStage 2 for all sub-tasks in one call1 system
planBuilds the step graph1 system
validate_planChecks agents, acyclic graph, inputs against schemas, budget0
executeRuns steps in dependency order, independent ones in parallel1 per step
reflectDecides whether more is needed1 system
synthesizeWrites the answer with citations1 system

A clean single-round request makes 4 system calls (intent, score, plan, synthesize) plus one call per domain step.

Request states

failed means nothing useful could be returned, for example intent analysis itself failed. If even one domain step succeeded, the request ends as partial, with an answer and a list of what is missing.

Retrieval

Stage 1: one SQL round trip per sub-task

  1. Embed the sub-task with the query prefix the embedding model expects. The vector is normalized, so cosine similarity is a dot product.
  2. Vector list: top 100 agents by the best match across their description and example vectors (pgvector HNSW index).
  3. Keyword list: top 100 by Postgres full-text rank on search_text. If true BM25 is needed later, a BM25 extension can replace this.
  4. Both lists are filtered inside the query: kind = 'domain' AND active, plus a domain filter when intent supplies one.
  5. Fuse with RRF (k = 60) and keep the top 50.

Stage 2: one scorer call for the whole request

Nexus sends every sub-task with its 50 candidates to nexus-scorer. Each candidate goes as a short summary: name, description cut to about 300 characters, and input field names. The scorer returns a score from 0 to 10 for each. Nexus keeps candidates scoring 6 or more, at least 3 and at most 10 per sub-task.

If the scorer fails

Nexus falls back to the top 5 by RRF order and carries on. Retrieval quality drops, but the request still gets answered.

Plans

The planner returns steps. A step's input can be a literal value or a reference to an earlier step's output. A reference with fan_out turns into one call per item.

{
  "steps": [
    { "id": "s1", "subtask": "a", "agent": "ip-reputation-lookup",
      "input": { "ip": "1.2.3.4" }, "depends_on": [] },
    { "id": "s2", "subtask": "b", "agent": "user-connection-search",
      "input": { "destination_ip": "1.2.3.4", "window": "30d" }, "depends_on": [] },
    { "id": "s3", "subtask": "b", "agent": "user-device-lookup",
      "input": { "user_id": { "from": "s2", "path": "$.users[*].id", "fan_out": true } },
      "depends_on": ["s2"] }
  ],
  "expects_follow_up": false
}

validate_plan rejects a plan when:

  • a step names an agent that wasn't among the candidates
  • the steps form a cycle
  • an input that is already known fails the agent's schema
  • the plan, counting fan-out, would go over the call budget

Nexus gives the planner one retry, passing the errors back. Inputs that come from earlier steps are checked again when they are filled in, just before each call.

Platform client

One shared poller per process keeps every open execution in a min-heap, ordered by when it is next due. A single async task takes the due entries, polls them with a limit on concurrent requests, and resolves the waiting call. Ten thousand open executions cost one task, not ten thousand.

Budgets and defaults

The platform reports no token usage or cost, so budgets count what Nexus can see. The caller can lower them per request.

LimitDefaultWhen hit
Reflection loops3Go to synthesis with what exists
Agent calls (system + domain)40Stop planning new steps, then synthesize
Wall-clock time per request180 sCancel open steps, then synthesize
Timeout per agent call120 sStep marked timed_out
Parallel steps per request8Extra steps wait their turn
Clarifying-question wait24 hRequest cancelled

Synthesis is always allowed to run, even after a budget is hit, so the caller always gets an answer from whatever was found.

Part 6

Building without LLM access

Nexus is developed against a fake AI Platform Service that follows the assumed API. Nexus cannot tell the two apart. Switching to the real platform is one setting, the base URL.

Testable now
  • Every path in the graph: one round, a reflection loop, partial failure, clarifying questions, budgets
  • Async polling, timeouts, and resuming after a restart
  • Stage 1 recall@50, since it needs only the embedding model
  • That every system-agent output matches its spec
Waits for LLM access
  • How well intent, scorer, planner and synthesizer actually perform
  • Real latency per call and polling tuning
  • A prompt-tuning pass on the system agents
